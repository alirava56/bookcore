# Runbook مدیریت رخداد و بازیابی

1. در رخداد Counter Drift یا نقص تاریخچه، نوشتن جدید همان Scope را از مسیر کنترل‌شده متوقف و شناسهٔ Tenant و Correlation ID را ثبت کنید. از حذف Booking/History خودداری کنید.
2. ابتدا Inspector فقط‌خواندنی را برای Tenant اجرا کنید. چون نمونه‌بردار است، خروجی `findings=[]` اثبات سلامت کل سازمان نیست.
3. برای Outbox قرنطینه‌شده، ابتدا با Credential مستقل `OUTBOX_OPS_DATABASE_URL` لیست Sanitized را ببینید. Payload و Secret در خروجی نیستند. قبل از Retry، علت و Predecessor را بررسی کنید.
4. تابع جدید `bookcore_requeue_outbox_bound` Actor را از `session_user` و Registry مشخص می‌کند؛ دلیل لازم است و فعالیت در Audit درج می‌شود. تابع قبلیِ دارای `p_actor` از دسترسی Ops خارج است.
5. اگر دعوت ساخته شد ولی پاسخ/Token گم شد: OWNER مجاز دعوت PENDING را از فهرست متادیتا پیدا کند، با دلیل ابطال کند و دعوت جدید صادر کند؛ توکن قدیمی قابل بازیابی نیست و نباید با Query یا log بازیابی شود.
6. اگر Commit نتیجهٔ نامعلوم دارد، موفقیت یا Rollback را ادعا نکنید؛ وضعیت Commit‌شده را با شناسهٔ عملیات و همان Idempotency Key بررسی کنید.
7. هر اقدام باید منشأ هویت عملیاتی، دلیل، وضعیت قبل و بعد و تأیید بعد از Commit داشته باشد.

این Runbook دستور تعمیر دستی خودکار ندارد؛ آزمایش‌های واقعی Failover و مدیریت Incident در انتشار نهایی الزامی‌اند.
